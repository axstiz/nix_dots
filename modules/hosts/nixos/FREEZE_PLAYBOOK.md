# Playbook: зависания / hard-off ноутбука Acer Aspire Lite AL15-42P (Barcelo, iGPU)

Живая справка: что сделано из экспериментов и что делать, если проблема
вернётся. Актуальность проверяется по последнему коммиту рядом с этим файлом.

## Текущий действующий набор

| Что | Где | Зачем |
|---|---|---|
| Ядро 6.18.60 (фаза D) | `modules/aspects/hardware.nix` + отдельный инпут `nixpkgs-kernel` | на 6.18.53 была серия «безмолвных» DCN/DMCUB-локапов |
| `amdgpu.dcdebugmask=0x812` (фаза F) | `modules/hosts/nixos/_hardware.nix` | разом выключены энергосберегающие оптимизации DCN: stutter (0x2) + PSR (0x10) + IPS (0x800) |
| `amdgpu.sg_display=0` (фаза F) | `modules/aspects/system.nix` | дисплейные буферы идут через GART: у iGPU всего 512 МБ dedicated VRAM, scatter-gather был под подозрением |
| `amdgpu.gpu_recovery=1` | `_hardware.nix` | автосброс GPU при подвисании колец — страховка (дисплейную прошивку не чинит) |
| `drm.debug=4` (временный) | `_hardware.nix` | kms-логи для улик при следующем падении; убрать первым после стабилизации |
| `cpu-cool` (фаза T) | `_hardware.nix`, systemd one-shot | boost=0 + частота зажимается на 2.3 ГГц; до лимита были thermal trip'ы (hard-off при burst 4.39 ГГц → 105 °C), после — Tctl 49–54 °C, GPU спит (400 МГц / 4 Вт) |
| Монитор @60 (эксперимент) | `modules/aspects/wm/home.nix` | изоляция HDMI-FRL/DSC-тракта; нативный режим — `2560x1440@144` |
| USB-хаб вынут | физически | исключён из фолл-истории (фолл повторился и без него) |

## Что уже исключено (не возвращаемся без необходимости)

- PSR — отключён, фоллы продолжались.
- USB-хаб — не причина (фолл случился при вынутом хабе).
- FRL/DSC-тракт — не причина (фолл на @60, где FRL/DSC не задействованы;
  кроме того фолл был «без внешнего монитора», на eDP).
- `amdgpu.dpm=0` — не добавлять: ломает ранний бут на Barcelo (проверено).
- Serpantinum/Hyprland — не первопричина по журналам (логи композитора в окне
  фоллов пусты), но окончательный тест — «Фаза S» ниже.

## Сценарий 1: снова полный hard-off («полностью отрубился»)

1. Основная гипотеза — thermal trip (Tj max 105 °C; до лимита Tctl держался
   73–77 °C на полузагруженной системе).
2. Проверки по порядку:
   - `sensors` сразу после старта (ожидают 45–55 °C — cpu-cool активен).
   - Под нагрузкой (браузер/opencode): `sensors` раз в 20 с — цель понять,
     доходит ли Tctl до 95+.
   - `journalctl -k -b -1 | tail`: при thermal trip журнал обрывается
     внезапно, без признаков штатного shutdown; при чистом выключении в хвосте
     виден systemd-shutdown.
3. Если hard-off случился при 50 °C — это НЕ температура:
   - питание/батарея: 12.65 В — живая, но проверить адаптер (вилку, второй
     кабель), убедиться, что работал от сети;
   - вентилятор: послушать/потрогать решётку, проверить, что не заблокирован.
4. Если thermal подтверждён и лимит мешает работе — поэтапное смягчение:
   - Шаг a: в юните `cpu-cool` включить `boost=1`, потолок оставить
     `3200000` (3.2 ГГц); сутки наблюдений через `sensors`.
   - Шаг b: если приемлемо — поднять потолок до `3600000` или убрать.
   - Параллельно: `nbfc-linux` — софтовое управление вентилятором для Acer
     (если есть конфиг под AL15-42P); откат — отключить сервис.
   - Долгосрочно: чистка радиатора / термопаста остаётся корневым решением.

## Сценарий 2: снова «зелёный/чёрный экран + замерший ввод» (DCN/DMCUB)

1. Записать время падения (HH:MM).
2. Улики из журнала:
   `journalctl -k -b -1 | grep -E "DMCUB|GPU recovery|hang|timeout"` —
   при активном `drm.debug=4` там же будет kms-след.
3. Если повторилось на 6.18.60 — по дешевизне:
   - Шаг A — уменьшить фазу F побитно: снять `0x800` (IPS), оставить `0x12`;
     затем снять `0x2`. Так найдём минимальный работающий бит-набор.
   - Шаг B — проверка Фазы S: убрать `hm.serpantinum` из `profiles.nix`
     (домашний профиль), reboot; 24–48 ч на голом Hyprland без шела.
   - Шаг C — BIOS: `support.acer.com` → Drivers → BIOS для AL15-42P. Сейчас
     стоит V1.22 (04/02/2025); если Acer выложил новее — обновить
     (Windows-инсталлер Acer или через BIOS). Там обычно живут DCN-фиксы.
   - Шаг D — сервис/железо: memtest, диагностика в мастерской.
4. После 2–3 дней чистой работы — откручивать эксперименты по одному:
   - первым убрать `drm.debug=4` (самый шумный);
   - затем `gpu_recovery=1`;
   - затем биты `dcdebugmask` до минимального набора; целиком уходить только
     после недели чистой работы на минимальном наборе.
5. Если всё чисто — вернуть нативный монитор `@144` в `wm/home.nix` и ещё
   сутки наблюдать.

## Быстрые команды

```sh
# Активные параметры ядра
cat /proc/cmdline

# Текущие температуры
sensors

# CPU-лимит: проверка и живое снятие (без пересборки)
cat /sys/devices/system/cpu/cpufreq/boost                          # 0 — лимит
sudo sh -c 'echo 1 > /sys/devices/system/cpu/cpufreq/boost;
  echo 4388000 > /sys/devices/system/cpu/cpu*/cpufreq/scaling_max_freq'

# Состояние юнита лимита
systemctl status cpu-cool

# Откат kernel-экспериментов: правка boot.kernelParams
# (modules/hosts/nixos/_hardware.nix и modules/aspects/system.nix) + switch

# Обновление ядра в будущем (через инпут nixpkgs-kernel)
nix flake lock --update-input nixpkgs-kernel && sudo nixos-rebuild switch
```

## Правила наблюдения за фоллами

- Хронология-частота: фиксируй периодичность падений (раз в день / час и 
  т. д.) — она связывает фоллы с фазами.

- Каждое новое падение фиксировать со временем и сообщать агенту (я вытащу
  контекст из журнала).
- эксперименты не запускать одновременно — строго по одному и с комментарием
  «фаза X» и датой (так уже лежит в `_hardware.nix` / `system.nix`).
- Каждое принятое изменение — коммит + пуш: репо обязано равняться живой
  системе.
